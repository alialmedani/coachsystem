# CoachApp — دليل تسليم المطوّر

> **الجمهور:** مطوّر يستلم الـ backend. تشرح هذه الوثيقة التقنيات والمعمارية وكل كيان (Entity)
> ونموذج المصادقة/العزل بين المستأجرين (Tenancy) وخدمات جهة المدرّب وجهة المتدرّب والقواعد
> الشاملة وكيفية البناء/التشغيل/التوسعة.
>
> **القاعدة الذهبية لهذا الكود:** *الكود هو المرجع.* عند اختلاف أي وثيقة مع الكود، **الكود يفوز**.
> الشريحة المرجعية التي تُحتذى هي **Trainee / WorkoutPlan** تحت `src/`.

> ملاحظة: تُبقي هذه الوثيقة أسماء الكلاسات والملفات والمسارات والمعرّفات البرمجية بالإنجليزية
> لأنها كود حرفي.

---

## 1. التقنيات والشكل العام

- **الإطار:** ABP Framework **10.4.0** على **.NET 10**.
- **القالب:** قالب ABP للتطبيق الواحد (`app`) — **وليس** القالب المعياري (modular). **لا يوجد
  مجلد `modules/`**؛ كل شيء تحت `src/`.
- **النمط:** شرائح عمودية (vertical slices) عمليّة بأسلوب **مجلّدات المزايا** (على غرار
  `../JasimExpress/express_api`).
- **قاعدة البيانات:** SQL Server، والمخطّط يُدار عبر **EF Core migrations** (لا SQL يدوي أبدًا).
- **المصادقة:** OpenIddict (خادم مصادقة + تحقّق من التوكن في نفس عملية الاستضافة).
- **تعدّد المستأجرين (Multi-tenancy):** مُفعّل — **مدرّب واحد = مستأجر واحد**.
- **التحويل (Mapping):** **Mapster** (لا AutoMapper/Mapperly).
- **الـ API:** **متحكّمات تلقائية (conventional controllers)** من ABP — تُنشر AppServices كـ REST
  تلقائيًّا؛ لا متحكّمات مكتوبة يدويًّا.
- **مُستبعَد عمدًا:** MediatR/CQRS، AutoMapper، Mapperly، FluentValidation، مستودعات مخصّصة لـ CRUD
  البسيط، وكلاسات `*Factory`/`*Manager` لـ CRUD البسيط.

> ⚠️ **مفارقة في التسمية:** مقطع المجلد وفضاء الأسماء مكتوب **`Entites`** (بحرف `i` ناقص). هذا
> مقصود وثابت في كل مكان — الكيان + DTOs + الواجهة تحت `CoachApp.Entites.<Feature>`. لا "تصلحه"؛
> ستكسر البناء.

## 2. تخطيط الحلّ (Solution)

| المشروع | المسؤولية |
|---|---|
| `CoachApp.Domain.Shared` | الثوابت (`Entites/<Feature>/`)، التعدادات (`Enums/`)، `CoachAppDomainErrorCodes`، الأدوار/البادئات، الترجمة (`Localization/CoachApp/*.json`) |
| `CoachApp.Domain` | الكيانات (`Entites/<Feature>/`)، بذور البيانات (seeders)، بذرة OpenIddict، حارس المدرّب الواحد |
| `CoachApp.Application.Contracts` | DTOs + `I<Entity>AppService` (`Entites/<Feature>/`)، الصلاحيات (`Permissions/`) |
| `CoachApp.Application` | AppServices (`Apis/<Feature>/`)، `CoachAppMapsterConfig`، `MapsterObjectMapper`، `MyTraineeAppServiceBase` |
| `CoachApp.EntityFrameworkCore` | `CoachAppDbContext`، `EntityConfigurations/<Feature>/`، `Migrations/` |
| `CoachApp.HttpApi` / `.HttpApi.Host` | المتحكّمات التلقائية، ربط الاستضافة، Swagger، المصادقة |
| `CoachApp.DbMigrator` | تطبيق كونسول: يطبّق الـ migrations ويزرع الأدوار/الصلاحيات/المشرف |

### اصطلاح فضاء الأسماء (يُسقَط اسم الطبقة)
- الكيان + DTOs + `I<Entity>AppService` → `CoachApp.Entites.<Feature>`
- AppService → `CoachApp.Apis.<Feature>`
- التعدادات → `CoachApp.Enums`
- إعداد EF → `CoachApp.EntityConfigurations.<Feature>`
- الصلاحيات → `CoachApp.Permissions`
- رموز الأخطاء → `CoachApp` (`CoachAppDomainErrorCodes`)

`<Feature>` هو اسم الكيان بصيغة الجمع (`Trainees`، `WorkoutPlans`…).

## 3. كيف يتدفّق الطلب

```
طلب HTTP
  → متحكّم ABP التلقائي (مولَّد من واجهة الـ AppService)
    → فحص صلاحية [Authorize] (على مستوى الكلاس + لكل ميثود)
      → AppService (Apis/<Feature>) — الطبقة "السمينة":
          • تحديد المستخدم/المستأجر الحالي (ICurrentUser / ICurrentTenant)
          • استعلام عبر IRepository<T,Guid>.GetQueryableAsync() + WhereIf + Dynamic.Core OrderBy + Skip/Take + AsyncExecuter
          • فحوص وجود/فرادة عبر التجميعات → رمي BusinessException(errorCode)
          • التغيير عبر static Create(...) / ميثودات السلوك (Add*, Clear*, Activate…)
          • الحفظ عبر IRepository<T,Guid>
          • تحويل الكيان → DTO بـ ObjectMapper.Map (يمرّ عبر Mapster)
          • إثراء DTOs ببيانات عرض عبر-تجميعية (أسماء التمارين/الأطعمة، مجاميع الماكروز)
  → استجابة DTO (تُسلسَل تلقائيًّا)
```

يُطبَّق تعدّد المستأجرين في الـ pipeline (`UseMultiTenancy`، بعد المصادقة)، فتُصفّى كل استعلامات
`IMultiTenant` تلقائيًّا للمستأجر الحالي — نادرًا ما تصفّي بـ `TenantId` يدويًّا.

## 4. نموذج المجال (Domain)

### 4.1 اصطلاحات عامّة عبر كل الكيانات
- **الجذور التجميعية (Aggregate roots):** `FullAuditedAggregateRoot<Guid>` + `IMultiTenant`
  (`public virtual Guid? TenantId`). تمنح Id، تدقيق الإنشاء/التعديل، **الحذف الناعم (soft delete)**،
  وعزل المستأجر.
- **الكيانات الابنة (المملوكة):** `Entity<Guid>`. مفتاحها الخلفي للأب `protected set` (يُضبط فقط
  عبر الباني). تُنشأ **حصرًا** عبر ميثودات `Add*` في الجذر — وهذا هو حدّ التجميعة.
- **التحقّق:** عبر `Check.NotNullOrWhiteSpace` / `Check.Length` من ABP مقابل الـ `*Consts` المشتركة
  (يرمي `ArgumentException`). الكيانات نفسها **لا** ترمي `BusinessException` — القواعد الحقيقية عبر
  التجميعات (خطة مفعّلة واحدة، "حدّ 100 مُدخَل"، وجود المراجع) تُفرَض في **طبقة التطبيق**.
- **المصنع + السلوك:** لكل جذر `static Create(Guid id, …, Guid? tenantId = null)`؛ وتغييرات الحالة
  عبر ميثودات سلوك (`Add*`، `Clear*`، `Activate`/`Deactivate`). لا `*Factory`/`*Manager`.

### 4.2 خريطة التجميعات

```
Trainee            (جذر؛ يرتبط بـ IdentityUser عبر UserId)   ── مستقل
Exercise           (جذر؛ مكتبة تمارين المدرّب)                ── مستقل
Food               (جذر؛ مكتبة أطعمة المدرّب)                 ── مستقل

WorkoutPlan               (جذر، TraineeId، IsActive)
 └─ WorkoutDay            (ScheduledDay: DayOfWeek?، Order)
     └─ WorkoutExercise   (→ Exercise، Sets/Reps/WeightKg/RestSeconds/Notes)

NutritionPlan             (جذر، TraineeId، IsActive، أهداف ماكروز يومية اختيارية)
 └─ Meal                  (Order)
     └─ MealItem          (→ Food، Quantity = عدد الحصص)

WorkoutPlanTemplate       (جذر؛ بلا TraineeId / بلا IsActive)   ── مخطَّط قابل لإعادة الاستخدام
 └─ WorkoutTemplateDay    (ScheduledDay يُنقل إلى النسخ)
     └─ WorkoutTemplateExercise (→ Exercise)

NutritionPlanTemplate     (جذر؛ بلا TraineeId / بلا IsActive؛ الأهداف تُنقل إلى النسخ)
 └─ NutritionTemplateMeal
     └─ NutritionTemplateItem (→ Food)

WorkoutLog                (جذر، TraineeId؛ WorkoutPlanId + WorkoutDayId اختياريان، Date)
 └─ WorkoutLogEntry       (→ Exercise؛ الفعلي + لقطة الموصوف PRESCRIBED)

NutritionLog              (جذر، TraineeId؛ NutritionPlanId اختياري، Date)
 └─ NutritionLogEntry     (→ Food، Quantity)

ProgressEntry             (جذر، TraineeId؛ وزن/دهون/مقاسات/تاريخ) ── مستقل
TraineeNote               (جذر، TraineeId؛ Date، Text؛ المؤلّف = CreatorId) ── مستقل
```

**الروابط عبر التجميعات مفاتيح Guid فقط** — لا تنقّل (navigation) عبر حدّ التجميعة.
`WorkoutExercise/WorkoutLogEntry/WorkoutTemplateExercise → Exercise`؛
`MealItem/NutritionLogEntry/NutritionTemplateItem → Food`؛ وكل الجذور المملوكة للمتدرّب →
`Trainee` عبر `TraineeId`.

### 4.3 ملاحظات مفتاحية عن الكيانات

- **`Trainee`** — ملف تدريبي علاقته 1:1 مع `IdentityUser` من ABP (دور `Trainee`) عبر `UserId`.
  بيانات الاعتماد على المستخدم، وبيانات التدريب هنا. `UserName` لقطة من اسم الدخول.
  `Activate()`/`Deactivate()` يبدّلان `IsActive`.
- **`WorkoutDay.ScheduledDay` (`DayOfWeek?`)** — يغذّي شاشة "اليوم". `null` = لا يظهر أبدًا كـ اليوم؛
  يومٌ أسبوعي بلا يوم مجدول = يوم راحة.
- **`WorkoutLogEntry`** — يخزّن **الفعلي** (`Sets/Reps/WeightKg/Notes`) *و* **لقطة الموصوف**
  (`PrescribedSets/PrescribedReps/PrescribedWeightKg`، تقبل null). تُلتقط اللقطة عند التسجيل من خطة
  فيبقى "المخطَّط مقابل المنجَز" حتى بعد تعديل الخطة. السجلّات اليدوية موصوفها null.
- **`MealItem`/`NutritionLogEntry`** يخزّنان فقط `FoodId` + `Quantity` (حصص). السعرات والماكروز
  **تُحسب من مكتبة `Food` وقت القراءة**، لا تُخزَّن على العنصر — فتعديل ماكروز طعامٍ يصحّح كل شيء رجعيًّا.
- **القوالب** تحاكي الخطط لكن تُسقط `TraineeId` و`IsActive` (لا مفهوم "مفعّل" لمخطَّط)، وتعيد استخدام
  `*Consts` الخاصّة بالخطط (لا كلاسات ثوابت مستقلّة).

### 4.4 التعدادات (`CoachApp.Enums`، تُخزَّن كـ `byte`)
- **Gender:** `Unspecified=0, Male=1, Female=2`
- **TrainingGoal:** `General=0, LoseWeight=1, BuildMuscle=2, Maintain=3, ImproveFitness=4, Strength=5`
- **MuscleGroup:** `Other=0, Chest=1, Back=2, Shoulders=3, Arms=4, Legs=5, Core=6, FullBody=7, Cardio=8`
- **Equipment:** `None=0, Bodyweight=1, Barbell=2, Dumbbell=3, Machine=4, Cable=5, Kettlebell=6, ResistanceBand=7, Other=8`
- إضافةً إلى `System.DayOfWeek` (يستخدمه `ScheduledDay`).

### 4.5 الثوابت (حدود أطوال الحقول — `Domain.Shared/Entites/…/*Consts.cs`)
`TraineeConsts` (UserName 256، First/Last 64، Email 256، Phone 32، Password 6–128)،
`ExerciseConsts` (Name 128، Desc 512، Instructions 2000، MediaUrl 512)،
`FoodConsts` (Name 128، Desc 512، ServingUnit 16)،
`WorkoutPlanConsts` (Name 128، Desc 512، DayName 64، Reps 32، Notes 512 — تستخدمها القوالب أيضًا)،
`NutritionPlanConsts` (Name 128، Desc 512، MealName 64 — تستخدمها القوالب أيضًا)،
`WorkoutLogConsts` (Reps 32، Notes 512، **MaxEntries 100**)،
`NutritionLogConsts` (Notes 512، **MaxEntries 100**)،
`ProgressEntryConsts` (Notes 512)، `TraineeNoteConsts` (Text 2000).

## 5. التخزين (EF Core)

- **`CoachAppDbContext`** واحد (`src/CoachApp.EntityFrameworkCore/EntityFrameworkCore/`). يستبدل
  DbContext الخاصّين بـ Identity وTenantManagement (`[ReplaceDbContext]`) لتتمكّن من الـ JOIN عبرها.
  اسم سلسلة الاتصال `Default`؛ بادئة الجداول `CoachAppConsts.DbTablePrefix = "App"`، مخطّط null.
- **21 `DbSet` مجاليًّا** (جذور + أبناء): Trainees، Exercises، Foods، WorkoutPlans / WorkoutDays /
  WorkoutExercises، WorkoutPlanTemplates / WorkoutTemplateDays / WorkoutTemplateExercises، WorkoutLogs
  / WorkoutLogEntries، NutritionPlans / Meals / MealItems، NutritionPlanTemplates /
  NutritionTemplateMeals / NutritionTemplateItems، NutritionLogs / NutritionLogEntries،
  ProgressEntries، TraineeNotes.
- لكل كيان `IEntityTypeConfiguration<T>` تحت `EntityConfigurations/<Feature>/`، وكلّها تُطبَّق تلقائيًّا
  عبر `builder.ApplyConfigurationsFromAssembly(...)` في `OnModelCreating`.
- الـ migrations في `CoachApp.EntityFrameworkCore/Migrations/`.

## 6. التحويل (Mapster)

- **`CoachAppMapsterConfig.Configure()`** — سطر `TypeAdapterConfig<Entity, Dto>.NewConfig()` واحد
  لكل تحويل، **كيان → DTO فقط**. الإنشاء/التحديث يمرّ عبر ميثودات سلوك التجميعة، لا عبر التحويل.
- **`MapsterObjectMapper : IAutoObjectMappingProvider`** — يمرّر `ObjectMapper.Map<…>()` عبر Mapster.
  مُسجَّل في `CoachAppApplicationModule`.
- **الإثراء (Enrichment)** منفصل عن التحويل: قيم العرض عبر-التجميعية (أسماء التمارين والأطعمة،
  مجاميع الماكروز) تُملأ في الـ AppService عبر مساعِدات مخصّصة — `WorkoutLogEnricher`،
  `NutritionPlanEnricher`، `NutritionLogEnricher`، `NutritionPlanTemplateEnricher` — تحمّل صفوف
  المكتبة المرجعية دفعةً واحدة. حساب ماكروز الحصّة معرَّف في مكان واحد لكل مجال.

## 7. المصادقة والهوية وتعدّد المستأجرين

### 7.1 OpenIddict (`Domain/OpenIddict/OpenIddictDataSeedContributor.cs`)
- نطاق (**scope**) API واحد: `CoachApp`.
- عميلان (**clients**) (يُزرَعان فقط إن كان ClientId مضبوطًا):
  - **`CoachApp_App`** — عميل عام يفعّل **منح كلمة المرور (password grant / ROPC)** إضافةً إلى
    authorization_code وclient_credentials وrefresh_token ومنحَي LinkLogin/Impersonation من ABP.
    هذا هو كيف يسجّل تطبيق الـ SPA/الموبايل دخول مدرّب أو متدرّب باسم مستخدم+كلمة مرور.
  - **`CoachApp_Swagger`** — authorization_code فقط، لواجهة Swagger.
- الاستضافة (`CoachAppHttpApiHostModule`): **تحقّق (validation)** OpenIddict بجمهور `CoachApp`،
  و`UseLocalServer()` — نفس العملية خادم مصادقة *و* خادم موارد. **المطالبات الديناميكية مفعّلة**
  (`IsDynamicClaimsEnabled = true`)، فتنعكس تغييرات الصلاحيات/الأدوار دون إعادة دخول. في الإنتاج
  يُحمَّل `openiddict.pfx` حقيقي (عبارة المرور من `AuthServer:CertificatePassPhrase`).

### 7.2 زرع الأدوار والصلاحيات
- ثوابت أسماء الأدوار (`Domain.Shared/CoachAppRoles.cs`): **`Coach`**، **`Trainee`**.
- بادئات الصلاحيات (`Domain.Shared/CoachAppPermissionPrefixes.cs`): `CoachApp.Coach`،
  `CoachApp.Trainee` (مكرَّرة هنا لأن Domain لا يمكنه الإشارة إلى كلاس صلاحيات الـ Contracts).
- **`Domain/Data/CoachAppDataSeedContributor.cs`** يعمل للمضيف ولكل مستأجر، ولكلٍّ يضمن وجود دورَي
  `Coach` و`Trainee` (بنطاق المستأجر) ويمنح **كامل شجرة `Coach.*`** لـ Coach و**كامل شجرة
  `Trainee.*`** لـ Trainee.
- **لا زرع مشرف مخصّص** — المشرف الافتراضي من `IdentityDataSeedContributor` في ABP، بقيادة
  `CoachAppDbMigrationService.SeedDataAsync` (بريد/كلمة مرور المشرف عبر `DataSeedContext`).
  الافتراضي: `admin@abp.io` / `1q2w3E*` (`CoachAppConsts`).
- يُنشأ **مستأجر تجريبي** (`"demo"`) فقط عند `CoachApp:SeedDemoTenant == true` (مضبوط في appsettings
  الخاصّ بـ **DbMigrator**؛ يجب أن يكون false/غائبًا في الإنتاج).

### 7.3 تعدّد المستأجرين — "مستأجر لكل مدرّب"
- `MultiTenancyConsts.IsEnabled = true`؛ الاستضافة تنادي `app.UseMultiTenancy()`.
- **كل مدرّب = مستأجر واحد.** مشرف المستأجر المزروع تلقائيًّا *هو* المدرّب. المتدرّبون مستخدمو
  `IdentityUser` إضافيون (دور `Trainee`) يُنشأون داخل ذلك المستأجر، كلٌّ مرتبط 1:1 بملف `Trainee`
  عبر `UserId`.
- **حارس المدرّب الواحد لكل مستأجر:** `Domain/Identity/SingleCoachPerTenantHandler.cs` — معالِج حدث
  محلّي على إنشاء/تحديث `IdentityUser`. إن كان التغيير سيجعل مستخدمًا ثانيًا مدرّبًا في المستأجر،
  يرمي `BusinessException(SecondCoachNotAllowed)` ويتراجع عن وحدة العمل. يقصّر المسار على مسارات
  الدخول/القفل/الملف الساخنة.
- **المستأجر/المستخدم الحالي** يحلّه ABP من التوكن في الـ pipeline؛ استخدم `ICurrentTenant` /
  `ICurrentUser`. البذور تبدّل السياق بـ `_currentTenant.Change(tenantId)`.

### 7.4 شجرة الصلاحيات (`Application.Contracts/Permissions/CoachAppPermissions.cs`)
مجموعة واحدة **`CoachApp`**. عُقد CRUD تُبنى بمساعِد `AddCrud` (`.Create/.Update/.Delete`).

**شخصية المدرّب (`CoachApp.Coach.*`)**
| العقدة | الأبناء |
|---|---|
| `Trainees` | Create، Update، Delete، **ResetPassword** |
| `Exercises`، `WorkoutPlans`، `WorkoutPlanTemplates`، `Foods`، `NutritionPlans`، `NutritionPlanTemplates` | Create، Update، Delete |
| `Progress`، `Notes` | Create، Update، Delete |
| `Tracking` | *(ورقة — قراءة فقط؛ مشتركة بين قراءات WorkoutLog وNutritionLog وTraineeDashboard)* |

**شخصية المتدرّب (`CoachApp.Trainee.*`)**
| العقدة | الأبناء |
|---|---|
| `MyProfile`، `MyDashboard`، `MyToday`، `MyWorkoutPlans`، `MyNutritionPlans`، `MyNotes` | *(ورقة)* |
| `WorkoutLogs`، `NutritionLogs` | Create، Update *(بلا Delete — الحذف يعتمد على الورقة/Default)* |
| `MyProgress` | Create *(Update يعيد استخدام Create؛ Delete يعتمد على Default)* |

عدم التماثل مقصود: للمدرّب CRUD كامل على المكتبات/الخطط/المتدرّبين المشتركة؛ وللمتدرّب قراءة +
تسجيل إلحاقي فقط (يسجّل نشاطه لكن لا يحذف السجلّ).

### 7.5 رموز الأخطاء (`Domain.Shared/CoachAppDomainErrorCodes.cs`)
مربوطة بالترجمة عبر `MapCodeNamespace("CoachApp", typeof(CoachAppResource))`. تُرمى كـ
`BusinessException(code)`؛ فيحصل العميل على رمز ثابت + رسالة مترجَمة.

| الرمز | الثابت | المعنى / مكان الفرض |
|---|---|---|
| `CoachApp:00001` | `TraineeNotFound` | الإشارة إلى متدرّب غير موجود (خطة/قياس/ملاحظة/لوحة) |
| `CoachApp:00002` | `ExercisesNotFound` | تمرين مُشار إليه غير موجود |
| `CoachApp:00003` | `FoodsNotFound` | طعام مُشار إليه غير موجود |
| `CoachApp:00004` | `ExerciseInUse` | مُنع الحذف — مستخدَم في خطة/قالب/سجلّ (عطّله بدلًا منه) |
| `CoachApp:00005` | `FoodInUse` | مُنع الحذف — مستخدَم في خطة/قالب/سجلّ |
| `CoachApp:00006` | `DuplicateScheduledDay` | يومَا تمرين على نفس يوم الأسبوع |
| `CoachApp:00007` | `SecondCoachNotAllowed` | مدرّب واحد لكل مستأجر (حارس الهوية) |
| `CoachApp:00008` | `CannotModifyCoachAuthoredProgress` | لا يعدّل/يحذف المتدرّب إلّا قياسات تقدّمه هو |

**الترجمة:** `en.json` و`ar.json` هما الزوج المُصان (يغطّيان كليًّا رموز الأخطاء + تسميات الصلاحيات +
الأدوار + التعدادات). توجد بذور لغات أخرى لكنها غالبًا غير مترجَمة.

### 8.1 كيف يُنشأ حساب دخول المتدرّب (`TraineeAppService.CreateAsync`)
يحقن `IRepository<Trainee,Guid>` + `IdentityUserManager`. في نداء واحد:
1. إنشاء `IdentityUser` في `CurrentTenant.Id` (البريد افتراضيًّا `{UserName}@coachapp.local`).
2. `CreateAsync(user, password)` → `AddToRoleAsync(user, "Trainee")`. أخطاء الهوية تظهر كـ
   `UserFriendlyException` (عبر `CheckIdentityErrors`).
3. بناء الملف بـ `Trainee.Create(...)` مربوطًا بـ `user.Id`؛ ثم الإدراج.
4. `ApplyLoginStateAsync(user, IsActive)` — المفعّل يزيل القفل؛ و**غير المفعّل يضع قفلًا دائمًا**
   فلا يستطيع المتدرّب الدخول. تُنادى من Create/Update/Delete.

`DeleteAsync` **تعطيل قابل للاسترجاع** (يضبط `IsActive=false` + يقفل الدخول؛ يُحفَظ السجلّ؛
إعادة التفعيل عبر `UpdateAsync`). `ResetPasswordAsync` تنفّذ `RemovePasswordAsync` +
`AddPasswordAsync` في وحدة عمل واحدة (بلا كلمة مرور حالية؛ اسم الدخول ثابت).

### 8.2 DashboardCalculator (مشترك، `Apis/Dashboards/DashboardCalculator.cs`، `internal static`)
يستخدمه **كلٌّ** من لوحة المدرّب ولوحة المتدرّب (الفرق الوحيد: المدرّب يمرّر معرّف متدرّب من الإدخال،
والمتدرّب يحلّه من المستخدم الحالي).
- **الالتزام الغذائي (يوم):** جمع الماكروز المستهلَكة عبر *كل* سجلّات ذلك اليوم؛ الهدف = أهداف الخطة
  المفعّلة الصريحة، وإلّا مجاميع الوجبات المحسوبة؛ `percent = consumed/target*100` (منزلة واحدة،
  **بلا سقف**، null إن لم تكن هناك خطة/هدف صفري). `OverallPercent = CaloriesPercent`.
- **الالتزام الغذائي (مدى):** `consumedTotal / (targetPerDay * daysLogged) * 100` — بمعدّل على الأيام
  المسجَّلة فعلًا.
- **إتمام التمارين:** `CompletedSessions` = أيام متمايزة فيها سجلّ ضمن المدى؛ `PlannedPerWeek` =
  أيام الأسبوع المجدولة المتمايزة للخطة المفعّلة؛ `Weeks = ceil(days/7)`؛ `CompletionPercent =
  completed/planned*100` (بلا سقف، null إن لم تكن هناك خطة مفعّلة).

## 9. خدمات جهة المتدرّب (`Apis/<Feature>/`، ببادئة `My`)

### 9.1 قاعدة "مَن أنا" — `MyTraineeAppServiceBase`
`src/CoachApp.Application/MyTraineeAppServiceBase.cs` (يمدّد `CoachAppAppService`). **المكان الوحيد**
الذي يُربَط فيه المستخدم الداخل بمتدرّب:
- `GetCurrentTraineeAsync()` / `GetCurrentTraineeIdAsync()` — يبحثان عن `Trainee` حيث
  `UserId == CurrentUser.GetId()`. لا صفّ Trainee → `EntityNotFoundException(typeof(Trainee))`.
- **ثابت أمني:** معرّف المتدرّب **يُشتقّ دائمًا من المستخدم الحالي، لا من إدخال العميل أبدًا.** لا يحمل
  أي DTO إنشاء/تحديث لجهة المتدرّب `TraineeId`. الوصول لبيانات متدرّب آخر يُعامَل بانتظام كـ **404**
  (معرّف غريب → `EntityNotFoundException`) فلا تُفصح الملكية.

### 9.3 شاشة "اليوم" (`MyTodayAppService.GetAsync`)
الإدخال يحمل `Date` اختياريًّا **بتوقيت العميل المحلّي** (لكي يحترم "اليوم" منطقة المتدرّب الزمنية؛
null → `UtcNow.Date`). كل شيء يُحلّ للمتدرّب الحالي. تركّب:
- **التمرين:** الخطة المفعّلة → أيام اليوم المجدولة (`Days.Where(d => d.ScheduledDay ==
  date.DayOfWeek)`)، `IsRestDay` (خطة مفعّلة لكن لا شيء مجدول اليوم)، وأحدث سجلّ تمرين لليوم
  (`AlreadyLoggedWorkoutToday`، `LatestWorkoutLog`).
- **التغذية:** الخطة المفعّلة (وجبات+أهداف) + `NutritionAdherence` لليوم (عبر `DashboardCalculator`)
  + `AlreadyLoggedNutritionToday`.
- يُقصَر التاريخ إلى `[2000-01-01, 2100-01-01]` لإبقاء حساب مدى اليوم بعيدًا عن تجاوز `DateTime`.

### 9.4 تدفّقات "التسجيل من الخطة" (لقطات من جهة الخادم، بصلاحية `Create`)
- **`CreateFromDayAsync(CreateWorkoutLogFromDayDto)`** — الـ DTO هو فقط `{WorkoutDayId, Date, Notes?}`.
  تُحلّ الملكية **عبر جذر الخطة** (`TraineeId == me && Days.Any(d => d.Id == WorkoutDayId)`؛ الغريب →
  404، ومعرّف الأب لا يُفصح). كل تمرين موصوف يصبح مُدخَل سجلّ يُبذَر **الفعلي فيه من، ولقطة الموصوف
  تساوي، Sets/Reps/WeightKg الخاصّة بالخطة**.
- **`CreateFromPlanAsync(CreateNutritionLogFromPlanDto)`** — `{NutritionPlanId, Date, Notes?}`؛ فحص
  ملكية، ثم **تفريد** الوجبات→العناصر إلى مُدخَلات مرتّبة (`FoodId` + `Quantity`).
- **حفظ لقطة الموصوف عند التحديث:** `UpdateAsync` يمسح المُدخَلات ويعيد بناءها من إدخال العميل، لكن
  قيم الموصوف تُلتقط مسبقًا بمفتاح `(ExerciseId, Order)` وتُستعاد — لا يستطيع إدخال العميل الكتابة فوق
  سجلّ الوصفة أبدًا.

## 13. قرارات تصميمية بارزة وبنود مفتوحة

- **الحذف = تعطيل** للمتدرّبين وعناصر المكتبة (قابل للاسترجاع؛ السجلّ محفوظ). المسح النهائي مؤجَّل
  (مُشار إليه V1.1).
- **المتدرّب يرى الخطط المفعّلة فقط** — غير المفعّلة/المؤرشفة/المسوّدة مخفيّة عن جهة المتدرّب (مؤجَّل
  إلى V1.1).
- **النسب بلا سقف** في اللوحات — تجاوز الهدف يبقى ظاهرًا (لا يُقصَر إلى 100%).
- **يُسمح بعدّة سجلّات في اليوم**؛ شاشة اليوم تُظهر الأحدث، واللوحات تجمعها.
- **ماكروز التغذية تُحسب دائمًا من مكتبة الأطعمة وقت القراءة** — لا تُنسخ على عناصر الخطة/السجلّ —
  فتصحيح طعامٍ ينتشر في كل مكان.
- **الموصوف مقابل الفعلي** مفهوم من الدرجة الأولى على سجلّات **التمرين** فقط؛ "من الخطة" في التغذية
  يصبح ببساطة المُدخَلات الفعلية (بلا مفهوم موصوف).
- **`en` + `ar`** هما الترجمتان المُصانتان بالكامل؛ بقية بذور اللغات غير مترجَمة غالبًا.
- **كتابة `Entites`** (المفارقة الإملائية) حاملة للبنية عبر فضاءات الأسماء والمجلّدات — أبقِها.
